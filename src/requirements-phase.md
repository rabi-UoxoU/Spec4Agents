## 需求阶段

<a id="ears-patterns"></a>

### EARS 模式（Easy Approach to Requirements Syntax）

EARS（Easy Approach to Requirements Syntax）是一种结构化的需求编写方法，通过使用标准化的语法模板来提高需求的清晰性和一致性。EARS 定义了 6 种基本模式，每种模式适用于不同类型的系统行为。

<a id="section-4-1-1"></a>

#### Ubiquitous（普遍性需求）

**定义**：描述系统在所有情况下都必须满足的行为，没有任何前提条件或触发事件。

**语法模板**：
```
THE <系统名称> SHALL <系统响应>
```

**适用场景**：
- 系统的基本功能和持续性行为
- 不依赖于特定条件或事件的需求
- 系统的基本约束和限制

**示例**：

1. **用户界面需求**：
   ```
   THE 系统 SHALL 以 UTC 格式显示所有时间戳
   ```

2. **性能需求**：
   ```
   THE API SHALL 在 100 毫秒内响应健康检查请求
   ```

3. **安全需求**：
   ```
   THE 系统 SHALL 使用 AES-256 加密所有静态数据
   ```

4. **数据完整性需求**：
   ```
   THE 数据库 SHALL 保持所有外键关系的引用完整性
   ```

<a id="section-4-1-2"></a>

#### Event-driven（事件驱动需求）

**定义**：描述当特定事件或触发条件发生时，系统必须执行的响应行为。

**语法模板**：
```
WHEN <触发事件> THEN <系统名称> SHALL <系统响应>
```

**适用场景**：
- 用户操作触发的行为
- 系统事件触发的响应
- 外部信号或消息触发的处理

**示例**：

1. **用户登录**：
   ```
   WHEN 用户提交有效凭证 THEN 系统 SHALL 生成 JWT 令牌并返回给用户
   ```

2. **文件上传**：
   ```
   WHEN 用户上传大于 10MB 的文件 THEN 系统 SHALL 拒绝上传并显示错误消息
   ```

3. **支付处理**：
   ```
   WHEN 支付交易完成 THEN 系统 SHALL 向用户发送确认邮件
   ```

4. **数据同步**：
   ```
   WHEN 数据库记录更新 THEN 系统 SHALL 向消息队列发布变更事件
   ```

<a id="section-4-1-3"></a>

#### State-driven（状态驱动需求）

**定义**：描述系统在特定状态下必须持续满足的行为，强调状态的持续性。

**语法模板**：
```
WHILE <系统状态> THE <系统名称> SHALL <系统响应>
```

**适用场景**：
- 系统在特定模式或状态下的行为
- 持续性的监控和控制
- 状态相关的约束和限制

**示例**：

1. **用户会话管理**：
   ```
   WHILE 用户会话处于活动状态 THE 系统 SHALL 每 15 分钟刷新一次认证令牌
   ```

2. **维护模式**：
   ```
   WHILE 系统处于维护模式 THE 系统 SHALL 对所有 API 请求返回 HTTP 503 状态
   ```

3. **数据处理**：
   ```
   WHILE 批处理任务正在运行 THE 系统 SHALL 阻止同一任务并发执行
   ```

4. **资源限制**：
   ```
   WHILE 数据库连接池已满 THE 系统 SHALL 将新连接请求加入队列
   ```

<a id="section-4-1-4"></a>

#### Unwanted event（不期望事件需求）

**定义**：描述当不期望的条件或错误发生时，系统必须采取的保护性或恢复性措施。

**语法模板**：
```
IF <非预期条件或事件> THEN <系统名称> SHALL <系统响应>
```

**适用场景**：
- 错误处理和异常情况
- 安全威胁的响应
- 系统故障的恢复
- 输入验证失败的处理

**示例**：

1. **认证失败**：
   ```
   IF 用户连续三次输入错误凭证 THEN 系统 SHALL 锁定账户 15 分钟
   ```

2. **数据验证错误**：
   ```
   IF API 请求包含无效 JSON THEN 系统 SHALL 返回 HTTP 400 状态及详细错误消息
   ```

3. **系统资源耗尽**：
   ```
   IF 可用内存低于 10% THEN 系统 SHALL 触发垃圾回收并记录警告
   ```

4. **网络连接失败**：
   ```
   IF 数据库连接失败 THEN 系统 SHALL 采用指数退避最多重试 3 次，再返回错误
   ```

<a id="section-4-1-5"></a>

#### Optional feature（可选特性需求）

**定义**：描述仅在特定功能或配置启用时才需要满足的行为。

**语法模板**：
```
WHERE <包含某功能或已设置某配置> THE <系统名称> SHALL <系统响应>
```

**适用场景**：
- 可配置的功能模块
- 可选的集成和插件
- 基于许可证或订阅级别的功能
- 环境特定的行为

**示例**：

1. **功能开关**：
   ```
   WHERE 已启用高级分析功能 THE 系统 SHALL 收集详细的用户交互指标
   ```

2. **集成配置**：
   ```
   WHERE 已配置邮件通知服务 THE 系统 SHALL 针对严重错误发送邮件告警
   ```

3. **订阅级别**：
   ```
   WHERE 用户订阅了高级服务 THE 系统 SHALL 允许每分钟最多 100 次 API 请求
   ```

4. **环境配置**：
   ```
   WHERE 系统运行于生产模式 THE 系统 SHALL 禁用调试日志
   ```

<a id="section-4-1-6"></a>

#### Complex（复杂需求）

**定义**：结合多个条件（事件和状态）来描述更复杂的系统行为，通常组合 Event-driven 和 State-driven 模式。

**语法模板**：
```
WHEN <触发事件> WHILE <系统状态> THE <系统名称> SHALL <系统响应>
```

或其他组合形式：
```
WHEN <触发事件> IF <条件> THEN <系统名称> SHALL <系统响应>
```

```
WHILE <系统状态> IF <非预期条件> THEN <系统名称> SHALL <系统响应>
```

**适用场景**：
- 需要多个前提条件的复杂业务逻辑
- 状态和事件共同决定的行为
- 复杂的工作流和流程控制

**示例**：

1. **事件 + 状态组合**：
   ```
   WHEN 用户尝试修改记录 WHILE 该记录被其他用户锁定 THEN 系统 SHALL 拒绝修改并显示锁定通知
   ```

2. **事件 + 条件组合**：
   ```
   WHEN 用户提交订单 IF 订单总额超过 $10,000 THEN 系统 SHALL 要求在处理前取得经理批准
   ```

3. **状态 + 不期望事件组合**：
   ```
   WHILE 文件正在上传 IF 网络连接中断 THEN 系统 SHALL 暂停上传，并在连接恢复后继续上传
   ```

4. **多条件复杂需求**：
   ```
   WHEN 用户请求导出数据 WHILE 系统负载超过 80% IF 导出大小超过 1GB THEN 系统 SHALL 将请求加入队列，在非高峰时段处理
   ```

<a id="ears-selection"></a>

### EARS 模式选择指南

选择合适的 EARS 模式对于编写清晰、准确的需求至关重要。以下是选择指南：

| 问题 | 推荐模式 |
|------|---------|
| 这个行为是否总是成立，没有任何前提条件？ | Ubiquitous |
| 这个行为是由特定事件触发的吗？ | Event-driven |
| 这个行为在特定状态下持续发生吗？ | State-driven |
| 这是对错误或异常情况的响应吗？ | Unwanted event |
| 这个行为仅在特定功能启用时才需要吗？ | Optional feature |
| 这个行为需要多个条件（事件+状态，或事件+条件）吗？ | Complex |

<a id="section-4-3"></a>

### EARS 模式最佳实践

1. **优先使用简单模式**：如果可以用简单模式（Ubiquitous、Event-driven、State-driven）表达，避免使用 Complex 模式

2. **保持原子性**：每个需求应该描述一个单一的系统行为，如果需求过于复杂，考虑拆分为多个需求

3. **明确触发条件**：在 Event-driven 和 Complex 模式中，确保触发事件清晰、可观察、可测试

4. **区分状态和事件**：
   - **状态**是持续的条件（例如："用户已登录"、"系统处于维护模式"）
   - **事件**是瞬时的发生（例如："用户点击按钮"、"收到 API 请求"）

5. **使用一致的术语**：在所有需求中使用术语表中定义的标准术语

6. **避免实现细节**：EARS 需求应该描述"做什么"（what），而不是"怎么做"（how）

**不好的示例**（包含实现细节）：
```
WHEN 用户登录 THEN 系统 SHALL 调用 AuthService.authenticate() 方法并将令牌存储到 Redis
```

**好的示例**（聚焦于行为）：
```
WHEN 用户使用有效凭证登录 THEN 系统 SHALL 创建已认证的会话并返回访问令牌
```

<a id="incose-quality-rules"></a>

### INCOSE 质量规则

INCOSE（International Council on Systems Engineering，国际系统工程协会）定义了一套需求质量规则,用于确保需求具备成功系统开发所需的特征。这些规则帮助识别和消除需求中的常见问题,提高需求文档的整体质量。

<a id="section-4-4-1"></a>

#### 核心质量特征

INCOSE 定义了 15 个需求质量特征,本文使用以下 9 个核心特征:

1. **Unambiguous**（明确的）
2. **Verifiable**（可验证的）
3. **Traceable**（可追溯的）
4. **Singular**（单一的）
5. **Necessary**（必要的）
6. **Complete**（完整的）
7. **Consistent**（一致的）
8. **Feasible**（可行的）
9. **Implementation-free**（实现无关的）

<a id="section-4-4-2"></a>

#### 规则 1：Unambiguous（明确性）

**定义**：需求必须只有一种解释方式,不能有歧义或多种理解。

**说明**：
- 避免使用模糊的词语（如"快速"、"高效"、"用户友好"）
- 使用精确的量化指标
- 避免使用可能有多种解释的术语
- 使用术语表中定义的标准术语

**违规示例**：
```
❌ THE 系统 SHALL 快速处理请求
```
**问题**："quickly"（快速）是模糊的,没有明确的标准。

**正确示例**：
```
✅ THE 系统 SHALL 在 200 毫秒内处理 95% 的 API 请求
```
**改进**：使用具体的时间指标和百分比,消除歧义。

---

**违规示例**：
```
❌ THE 系统 SHALL 提供良好的用户体验
```
**问题**："good user experience"（良好的用户体验）是主观的,无法量化。

**正确示例**：
```
✅ THE 系统 SHALL 在用户提交查询后 2 秒内显示搜索结果
✅ THE 系统 SHALL 将系统可用性量表（SUS）得分保持在 80 分以上
```
**改进**：使用可测量的指标替代主观描述。

**补充示例与说明**：

**违规示例**：
```
THE 系统 SHALL 快速响应用户请求
```
**问题**："quickly"（快速）是模糊的，没有明确的标准。

**正确示例**：
```
THE 系统 SHALL 在 200 毫秒内响应 95% 的用户请求
```

**违规示例**：
```
THE 系统 SHALL 支持大量并发用户
```
**问题**："many"（许多）是模糊的数量。

**正确示例**：
```
THE 系统 SHALL 支持至少 10,000 个并发用户
```



<a id="section-4-4-3"></a>

#### 规则 2：Verifiable（可验证性）

**定义**：需求必须可以通过测试、检查、分析或演示来验证是否满足。

**说明**：
- 每个需求都应该有明确的验证方法
- 避免使用无法测试的词语（如"最大化"、"最小化"、"优化"）
- 确保验证标准是客观的、可重复的
- 考虑验证的成本和可行性

**违规示例**：
```
❌ THE 系统 SHALL 最大化系统可用时间
```
**问题**："maximize"（最大化）没有明确的成功标准,无法验证何时达到要求。

**正确示例**：
```
✅ THE 系统 SHALL 按每个自然月统计保持 99.9% 的可用时间
```
**改进**：提供具体的可测量目标和测量方法。

---

**违规示例**：
```
❌ THE 系统 SHALL 易于维护
```
**问题**："easy to maintain"（易于维护）是主观的,无法客观验证。

**正确示例**：
```
✅ THE 系统 SHALL 允许修改配置而无需重新编译代码
✅ THE 系统 SHALL 提供能够在 10 分钟内完成的自动化部署脚本
```
**改进**：将抽象概念转化为具体的、可验证的行为。

**补充示例与说明**：

**违规示例**：
```
THE 系统 SHALL 对用户友好
```
**问题**："user-friendly"（用户友好）是主观的，无法客观验证。

**正确示例**：
```
THE 系统 SHALL 允许用户在不超过 3 次点击内完成结账流程
```

**违规示例**：
```
THE 系统 SHALL 保证安全
```
**问题**："secure"（安全）过于宽泛，无法验证。

**正确示例**：
```
需求 1: THE 系统 SHALL 执行密码复杂度要求（至少 12 个字符，包含大写字母、小写字母、数字和特殊字符）
需求 2: THE 系统 SHALL 对每个 IP 地址实施每分钟 100 次请求的速率限制
需求 3: THE 系统 SHALL 记录所有认证尝试，并包含时间戳和来源 IP
```



<a id="section-4-4-4"></a>

#### 规则 3：Traceable（可追溯性）

**定义**：需求必须能够追溯到其来源（业务目标、用户需求、法规等）,并能够追踪到设计、实现和测试。

**说明**：
- 每个需求应该有唯一的标识符
- 需求应该引用其来源或依据
- 需求应该能够链接到相关的设计元素和测试用例
- 维护需求追溯矩阵

**违规示例**：
```
❌ The system must encrypt data
```
**问题**：没有标识符,没有说明为什么需要加密,无法追溯来源。

**正确示例**：
```
✅ **需求 1.3：数据加密**（来源：GDPR 第 32 条、安全策略 SP-2023-001）

THE 系统 SHALL 使用 AES-256 加密所有静态的个人身份信息（PII）

_追溯：业务需求 BR-1.2, 安全标准 SEC-001_
```
**改进**：包含需求编号、来源引用和追溯信息。

---

**违规示例**：
```
❌ Users should be able to export data
```
**问题**：没有编号,没有上下文,无法追溯到业务需求或用户故事。

**正确示例**：
```
✅ **需求 2.5：数据导出**（来源：用户故事 US-12）

WHEN 用户请求导出数据 THEN 系统 SHALL 在 30 秒内生成包含用户全部数据的 CSV 文件

_追溯：用户故事 US-12, 设计文档 DD-2.3, 测试用例 TC-25_
```
**改进**：明确的编号、来源和追溯链接。

**补充示例与说明**：

**示例**：
```markdown
### 需求 1：用户认证

#### 1.1 登录功能
WHEN 用户提交有效凭证 THEN 系统 SHALL 认证用户并创建会话

#### 1.2 登出功能
WHEN 用户退出登录 THEN 系统 SHALL 终止会话并清除认证令牌

### 需求 2：会话管理

#### 2.1 会话超时
WHILE 用户会话连续 30 分钟无活动 THE 系统 SHALL 自动终止会话
```



<a id="section-4-4-5"></a>

#### 规则 4：Singular（单一性）

**定义**：每个需求应该只表达一个单一的条件或行为,不应该包含多个需求。

**说明**：
- 避免使用"and"、"or"连接多个不同的需求
- 每个需求应该独立可测试
- 如果需求包含多个条件,考虑拆分为多个需求
- 使用 EARS 模式保持需求的原子性

**违规示例**：
```
❌ WHEN 用户登录 THEN 系统 SHALL 认证用户、创建会话、记录事件并发送通知邮件
```
**问题**：包含四个不同的行为,应该拆分为独立的需求。

**正确示例**：
```
✅ **需求 1.1：用户认证**
WHEN 用户提交登录凭证 THEN 系统 SHALL 对照用户数据库验证凭证

✅ **需求 1.2：会话创建**
WHEN 用户认证成功 THEN 系统 SHALL 创建超时时间为 30 分钟的新会话

✅ **需求 1.3：登录日志**
WHEN 用户成功登录 THEN 系统 SHALL 记录该事件，并包含时间戳和用户 ID

✅ **需求 1.4：登录通知**
WHEN 用户从新设备成功登录 THEN 系统 SHALL 向用户注册邮箱发送通知邮件
```
**改进**：将复合需求拆分为四个独立的、可单独测试的需求。

---

**违规示例**：
```
❌ THE 系统 SHALL 支持 CSV 和 JSON 导出格式，并允许用户计划导出时间
```
**问题**：包含两个不同的功能（格式支持和调度功能）。

**正确示例**：
```
✅ **需求 2.1：导出格式支持**
THE 系统 SHALL 支持以 CSV 和 JSON 格式导出数据

✅ **需求 2.2：导出调度**
THE 系统 SHALL 允许用户按每日、每周或每月的间隔安排自动数据导出
```
**改进**：拆分为两个独立的需求,每个关注一个功能。

**补充示例与说明**：

**违规示例**：
```
WHEN 用户提交订单 THEN 系统 SHALL 验证订单、处理支付、更新库存并发送确认邮件
```
**问题**：一个需求描述了四个不同的行为。

**正确示例**：
```
需求 1: WHEN 用户提交订单 THEN 系统 SHALL 验证订单数据
需求 2: WHEN 订单验证通过 THEN 系统 SHALL 处理支付
需求 3: WHEN 支付成功 THEN 系统 SHALL 更新库存
需求 4: WHEN 订单完成 THEN 系统 SHALL 向用户发送确认邮件
```



<a id="section-4-4-6"></a>

#### 规则 5：Necessary（必要性）

**定义**：每个需求都必须有明确的业务价值或技术必要性,不应包含不必要的需求。

**说明**：
- 每个需求应该能够追溯到业务目标或用户需求
- 避免"镀金"（添加不必要的功能）
- 质疑每个需求的存在理由
- 如果无法解释需求的必要性,考虑删除它

**违规示例**：
```
❌ THE 系统 SHALL 显示包含旋转标志的加载动画
```
**问题**：过于具体的实现细节,可能不是真正必要的需求。

**正确示例**：
```
✅ THE 系统 SHALL 在完成耗时超过 1 秒的操作期间向用户提供视觉反馈
```
**改进**：关注真正的需求（用户反馈）,而不是具体的实现方式。

---

**违规示例**：
```
❌ THE 系统 SHALL 为所有按钮使用蓝色配色
```
**问题**：这是设计决策,不是功能需求,除非有特定的业务或可访问性理由。

**正确示例**：
```
✅ THE 系统 SHALL 将文字与背景的对比度保持在至少 4.5:1，以符合 WCAG 2.1 Level AA 标准
```
**改进**：关注必要的可访问性需求,而不是任意的设计选择。

**补充示例与说明**：

**违规示例**：
```
THE 系统 SHALL 拥有美观的用户界面
```
**问题**："beautiful"（美观）是主观的，不是必要的功能需求。

**正确示例**：
```
THE 系统 SHALL 符合 WCAG 2.1 Level AA 无障碍标准
```



<a id="section-4-4-7"></a>

#### 规则 6：Complete（完整性）

**定义**：需求必须包含所有必要的信息,不应遗漏关键细节。

**说明**：
- 需求应该回答"谁"、"什么"、"何时"、"在什么条件下"
- 包含所有必要的前提条件和后置条件
- 定义所有相关的边界条件和限制
- 不应该有待定（TBD）或待确定（TBC）的内容

**违规示例**：
```
❌ WHEN 用户上传文件 THEN 系统 SHALL 验证文件
```
**问题**：没有说明验证什么（文件类型？大小？内容？）,验证失败时怎么办。

**正确示例**：
```
✅ WHEN 用户上传文件 THEN 系统 SHALL 验证以下条件：
   - The file size does not exceed 10MB
   - The file format is one of: PDF, DOCX, TXT, or CSV
   - The file name contains only alphanumeric characters, hyphens, and underscores

IF 验证失败 THEN 系统 SHALL 拒绝上传并显示说明具体失败原因的错误消息
```
**改进**：明确所有验证标准和失败处理。

---

**违规示例**：
```
❌ THE 系统 SHALL 向用户发送通知
```
**问题**：缺少关键信息：什么时候发送？通过什么渠道？什么内容？

**正确示例**：
```
✅ WHEN 用户账户余额低于 $10 THEN 系统 SHALL 在 5 分钟内向用户注册邮箱发送邮件通知，其中包含当前余额和充值链接
```
**改进**：包含触发条件、通知渠道、时间要求和内容要求。

**补充示例与说明**：

**不完整示例**：
```
WHEN 用户使用有效凭证登录 THEN 系统 SHALL 授予访问权限
```
**问题**：只描述了成功情况，没有描述失败情况。

**完整示例**：
```
需求 1: WHEN 用户使用有效凭证登录 THEN 系统 SHALL 授予访问权限并创建会话
需求 2: WHEN 用户使用无效凭证登录 THEN 系统 SHALL 拒绝访问并显示错误消息
需求 3: IF 用户三次输入错误凭证 THEN 系统 SHALL 锁定账户 15 分钟
```



<a id="section-4-4-8"></a>

#### 规则 7：Consistent（一致性）

**定义**：需求不应与其他需求或已知约束相冲突。

**说明**：
- 需求之间不应有逻辑矛盾
- 使用一致的术语和定义
- 确保需求与系统约束和外部标准一致
- 定期审查需求集以识别冲突

**违规示例**：
```
❌ 需求 1.1: THE 系统 SHALL 将所有用户数据存储在云端
❌ 需求 1.2: THE 系统 SHALL 在没有互联网连接时运行
```
**问题**：两个需求相互矛盾,无法同时满足。

**正确示例**：
```
✅ 需求 1.1: THE 系统 SHALL 在互联网连接可用时将用户数据同步到云存储
✅ 需求 1.2: THE 系统 SHALL 在本地缓存用户数据，并在互联网连接不可用时以离线模式运行
```
**改进**：解决冲突,明确在线和离线模式的行为。

---

**违规示例**：
```
❌ 需求 2.1: THE 系统 SHALL 在 500 毫秒内完成用户认证
❌ 需求 2.2: THE 系统 SHALL 对所有登录尝试执行包含短信验证的多因素认证
```
**问题**：SMS 验证通常需要几秒钟,与 500 毫秒的要求不一致。

**正确示例**：
```
✅ 需求 2.1: THE 系统 SHALL 在 500 毫秒内完成初始凭证验证
✅ 需求 2.2: WHEN 已启用多因素认证 THEN 系统 SHALL 在 10 秒内发送短信验证码，并允许用户在最多 5 分钟内完成验证
```
**改进**：区分不同的认证阶段,设置合理的时间要求。

**补充示例与说明**：

**违规示例**：
```
需求 1: THE 系统 SHALL 使用 TLS 1.3 加密所有传输中的数据
需求 2: THE 系统 SHALL 支持使用 SSL 3.0 的旧客户端
```
**问题**：TLS 1.3 和 SSL 3.0 不兼容，两个需求冲突。

**正确示例**：
```
需求 1: THE 系统 SHALL 使用 TLS 1.2 或更高版本加密所有传输中的数据
需求 2: THE 系统 SHALL 拒绝使用 SSL 3.0 或更早版本的客户端连接
```



<a id="section-4-4-9"></a>

#### 规则 8：Feasible（可行性）

**定义**：需求必须在给定的技术、时间和资源约束下可以实现。

**说明**：
- 考虑技术限制和物理定律
- 评估实现成本和时间
- 确保需求不违反已知的技术约束
- 与技术团队验证可行性

**违规示例**：
```
❌ THE 系统 SHALL 以 100% 的准确率预测用户行为
```
**问题**：100% 准确的预测在实践中是不可能的,违反了统计学和机器学习的基本原理。

**正确示例**：
```
✅ THE 系统 SHALL 根据历史转化数据衡量，以至少 75% 的准确率预测用户购买意向
```
**改进**：设置现实可达的目标,基于行业标准和历史数据。

---

**违规示例**：
```
❌ THE 系统 SHALL 在单台服务器上每秒处理 100 万笔交易
```
**问题**：对于大多数硬件配置,这个性能目标是不现实的。

**正确示例**：
```
✅ THE 系统 SHALL 使用可水平扩展的架构，通过多台服务器负载均衡，每秒处理至少 10,000 笔交易
```
**改进**：设置可行的性能目标,并说明实现方式（水平扩展）。

**补充示例与说明**：

**违规示例**：
```
THE 系统 SHALL 以 100% 的准确率预测用户行为
```
**问题**：100% 准确预测是不可能的。

**正确示例**：
```
THE 系统 SHALL 基于历史数据以至少 85% 的准确率预测用户行为
```



<a id="section-4-4-10"></a>

#### 实现无关性（Implementation-free）

**规则**：需求应该描述"做什么"（what），而不是"怎么做"（how）。

**说明**：需求不应该规定具体的实现技术、算法或架构，这些属于设计阶段的决策。

**违规示例**：
```
THE 系统 SHALL 使用 PostgreSQL 数据库存储用户数据
```
**问题**：规定了具体的数据库技术，限制了设计选择。

**正确示例**：
```
THE 系统 SHALL 持久化用户数据，并提供 ACID 事务保证
```

**违规示例**：
```
WHEN 用户提交表单 THEN 系统 SHALL 调用 validateInput() 函数
```
**问题**：规定了具体的函数名称，这是实现细节。

**正确示例**：
```
WHEN 用户提交表单 THEN 系统 SHALL 在处理前验证所有输入字段
```


<a id="quality-application"></a>

### INCOSE 质量规则应用指南

<a id="section-4-5-1"></a>

#### 需求审查检查清单

在编写或审查需求时,使用以下检查清单确保符合 INCOSE 质量规则：

**明确性检查**：
- [ ] 需求中是否有模糊的词语（快速、高效、用户友好等）？
- [ ] 所有量化指标是否明确？
- [ ] 术语是否在术语表中定义？

**可验证性检查**：
- [ ] 如何验证这个需求？（测试、检查、分析、演示）
- [ ] 验证标准是否客观且可重复？
- [ ] 是否避免了"最大化"、"最小化"等无法验证的词语？

**可追溯性检查**：
- [ ] 需求是否有唯一标识符？
- [ ] 需求是否引用了来源（用户故事、业务目标、法规）？
- [ ] 需求是否链接到相关的设计和测试？

**单一性检查**：
- [ ] 需求是否只表达一个条件或行为？
- [ ] 是否可以拆分为更小的独立需求？
- [ ] 需求是否可以独立测试？

**必要性检查**：
- [ ] 为什么需要这个需求？
- [ ] 需求是否追溯到业务目标或用户需求？
- [ ] 如果删除这个需求,会有什么影响？

**完整性检查**：
- [ ] 需求是否包含所有必要的信息？
- [ ] 是否定义了所有前提条件和后置条件？
- [ ] 是否有待定（TBD）的内容？

**一致性检查**：
- [ ] 需求是否与其他需求冲突？
- [ ] 术语使用是否一致？
- [ ] 需求是否与系统约束一致？

**可行性检查**：
- [ ] 需求在技术上可行吗？
- [ ] 需求在预算和时间约束内可实现吗？
- [ ] 是否与技术团队验证过可行性？

<a id="section-4-5-2"></a>

#### 常见质量问题和解决方法

| 问题类型 | 识别方法 | 解决方法 |
|---------|---------|---------|
| 模糊需求 | 包含"快速"、"高效"等词 | 用具体的量化指标替换 |
| 复合需求 | 包含多个"and"或"or" | 拆分为多个独立需求 |
| 不可验证 | 无法定义测试方法 | 添加可测量的验收标准 |
| 实现细节 | 指定具体技术或方法 | 重写为功能需求 |
| 缺少上下文 | 没有前提条件或触发事件 | 使用 EARS 模式添加上下文 |
| 不一致术语 | 同一概念使用不同词语 | 使用术语表标准化术语 |
| 过度约束 | 限制了实现选择 | 关注"做什么"而非"怎么做" |
| 缺少错误处理 | 只描述正常流程 | 添加异常和错误情况的需求 |

<a id="section-4-5-3"></a>

#### 质量改进示例

**原始需求**（存在多个质量问题）：
```
❌ The system should quickly process user requests and handle errors appropriately
```

**问题分析**：
- ❌ 不明确："quickly"（快速）是模糊的
- ❌ 不可验证：没有具体的性能指标
- ❌ 不单一：包含两个不同的需求（处理请求和错误处理）
- ❌ 不完整：没有说明什么类型的请求,什么类型的错误
- ❌ 使用"should"而非"SHALL"

**改进后的需求**：
```
✅ **需求 3.1：请求处理性能**
THE 系统 SHALL 处理用户 API 请求，响应时间中位数为 200 毫秒，第 95 百分位响应时间为 500 毫秒

✅ **需求 3.2：请求超时处理**
IF API 请求处理超过 30 秒 THEN 系统 SHALL 终止请求并返回 HTTP 504 Gateway Timeout 状态

✅ **需求 3.3：错误响应格式**
WHEN 请求处理期间发生错误 THEN 系统 SHALL 返回包含错误码、错误消息和请求 ID 的 JSON 响应
```

**改进说明**：
- ✅ 明确：使用具体的时间指标（200ms、500ms、30s）
- ✅ 可验证：可以通过性能测试验证
- ✅ 单一：拆分为三个独立的需求
- ✅ 完整：明确了请求类型、超时值和错误响应格式
- ✅ 使用"SHALL"表示强制性需求

<a id="section-4-6"></a>

### EARS 模式与 INCOSE 质量规则的结合

EARS 模式和 INCOSE 质量规则是互补的：

- **EARS 模式**提供了需求的**结构和语法**
- **INCOSE 质量规则**确保需求的**质量和特征**

**最佳实践**：

1. **先使用 EARS 模式**构建需求的基本结构
2. **然后应用 INCOSE 质量规则**检查和改进需求质量
3. **迭代优化**直到需求同时满足结构和质量要求

**示例工作流**：

```
步骤 1：使用 EARS 模式编写初始需求
WHEN 用户上传文件 THEN 系统 SHALL 处理该文件

步骤 2：应用 INCOSE 质量规则检查
- 明确性：❌ "process"（处理）是模糊的
- 完整性：❌ 缺少文件类型、大小限制、处理时间
- 可验证性：❌ 没有明确的验证标准

步骤 3：改进需求
WHEN 用户上传文件 THEN 系统 SHALL：
- 验证文件格式属于 PDF、DOCX 或 TXT
- 验证文件大小不超过 10MB
- 在 5 秒内提取文本内容
- 将提取文本存入数据库

IF 验证失败 THEN 系统 SHALL 拒绝上传并返回说明具体失败原因的错误消息

步骤 4：最终审查
✅ 使用 EARS Event-driven 模式
✅ 明确：所有操作都有具体定义
✅ 可验证：可以测试格式、大小、时间和存储
✅ 完整：包含正常流程和错误处理
✅ 单一：可以考虑拆分为多个需求以提高单一性
```

<a id="requirements-template"></a>

### requirements.md 模板

本节提供 `requirements.md` 文档的标准模板，包含所有必需章节和格式规范。

<a id="section-4-5-1-template"></a>

#### 模板结构

完整模板见[标准 requirements.md 模板](reference.md#template-requirements)。

<a id="section-4-5-2-template"></a>

#### 章节说明

##### 简介章节

**目的**：提供功能的高层次概述，帮助读者快速理解功能的背景和价值。

**内容要求**：
- 1-2 段文字
- 说明功能的目的和业务价值
- 说明功能的范围（包含什么，不包含什么）
- 可选：说明功能的利益相关者

**示例**：
```markdown
## 简介

本功能为电商平台添加用户认证系统，使用户能够安全地登录、管理会话和访问个人账户。认证系统是平台安全架构的核心组件，为后续的授权、个性化和订单管理功能提供基础。

该功能包括用户注册、登录、登出、会话管理和密码重置。不包括社交媒体登录（如 Google、Facebook 登录），这将在后续版本中实现。
```

##### 术语表章节

**目的**：定义文档中使用的关键术语，确保所有人对术语有共同理解，避免歧义。

**内容要求**：
- 使用项目符号列表
- 每个术语包含中文名称和英文名称（如果适用）
- 提供清晰、简洁的定义
- 按字母顺序或逻辑顺序排列

**格式**：
```markdown
- **术语中文名**（English Term）: 定义说明
```

**示例**：
```markdown
## 术语表

- **用户**（User）: 在系统中注册并拥有账户的个人
- **会话**（Session）: 用户登录后到登出或超时之间的时间段，期间用户保持认证状态
- **访问令牌**（Access Token）: 用于验证用户身份的短期凭证，通常为 JWT 格式
- **刷新令牌**（Refresh Token）: 用于获取新访问令牌的长期凭证，存储在安全的 HTTP-only cookie 中
- **凭证**（Credentials）: 用户用于认证的信息，通常包括用户名和密码
- **认证**（Authentication）: 验证用户身份的过程
- **授权**（Authorization）: 确定已认证用户可以访问哪些资源的过程
```

##### 需求章节

**目的**：详细描述系统必须满足的所有功能性和非功能性需求。

**内容要求**：
- 使用层次化的编号系统（需求 1, 需求 2, 需求 3...）
- 每个需求包含用户故事和验收标准
- 验收标准使用 EARS 模式编写
- 验收标准使用编号列表（1, 2, 3...）

**用户故事格式**：
```
作为 <角色>，我希望 <功能>，以便 <业务价值>
```

**示例**：
```markdown
## 需求

### 需求 1: 用户登录

**用户故事**: 作为注册用户，我希望能够使用用户名和密码登录系统，以便访问我的个人账户和订单历史。

#### 验收标准

1. WHEN 用户提交有效凭证 THEN 系统 SHALL 认证用户并返回访问令牌
2. WHEN 用户提交无效凭证 THEN 系统 SHALL 返回错误消息并拒绝访问
3. IF 用户连续三次输入错误凭证 THEN 系统 SHALL 锁定账户 15 分钟
4. THE 系统 SHALL 使用 bcrypt 对所有密码进行哈希处理，成本因子至少为 12
5. WHEN 用户成功登录 THEN 系统 SHALL 创建包含过期时间的会话记录

### 需求 2: 会话管理

**用户故事**: 作为系统管理员，我希望系统能够自动管理用户会话的生命周期，以便确保安全性和资源的有效利用。

#### 验收标准

1. WHILE 用户会话处于活动状态 THE 系统 SHALL 每 15 分钟刷新一次访问令牌
2. WHILE 用户会话连续 30 分钟无活动 THE 系统 SHALL 自动终止会话
3. WHEN 用户退出登录 THEN 系统 SHALL 使访问令牌失效并删除会话记录
4. THE 系统 SHALL 限制每个用户最多拥有 5 个并发会话
5. WHEN 用户超过会话数量上限 THEN 系统 SHALL 终止最早的会话

### 需求 3: 密码重置

**用户故事**: 作为忘记密码的用户，我希望能够通过电子邮件重置密码，以便重新获得账户访问权限。

#### 验收标准

1. WHEN 用户请求重置密码 THEN 系统 SHALL 向用户注册邮箱发送重置链接
2. THE 系统 SHALL 生成有效期为 1 小时的唯一限时重置令牌
3. WHEN 用户点击重置链接 THEN 系统 SHALL 验证令牌并允许用户设置新密码
4. IF 重置令牌已过期 THEN 系统 SHALL 拒绝重置请求，并提示用户申请新链接
5. WHEN 用户成功重置密码 THEN 系统 SHALL 使该用户所有现有会话失效
```

<a id="section-4-5-3-template"></a>

#### 完整示例：用户认证功能

以下是一个完整的 `requirements.md` 文档示例：

```markdown
# 需求文档：用户认证系统

## 简介

本功能为电商平台添加用户认证系统，使用户能够安全地登录、管理会话和访问个人账户。认证系统是平台安全架构的核心组件，为后续的授权、个性化和订单管理功能提供基础。

该功能包括用户注册、登录、登出、会话管理和密码重置。不包括社交媒体登录（如 Google、Facebook 登录）和多因素认证（MFA），这些将在后续版本中实现。

## 术语表

- **用户**（User）: 在系统中注册并拥有账户的个人
- **会话**（Session）: 用户登录后到登出或超时之间的时间段，期间用户保持认证状态
- **访问令牌**（Access Token）: 用于验证用户身份的短期凭证，采用 JWT 格式，有效期 15 分钟
- **刷新令牌**（Refresh Token）: 用于获取新访问令牌的长期凭证，存储在安全的 HTTP-only cookie 中，有效期 7 天
- **凭证**（Credentials）: 用户用于认证的信息，包括用户名（或电子邮件）和密码
- **认证**（Authentication）: 验证用户身份的过程
- **会话超时**（Session Timeout）: 用户在一段时间内没有活动后，系统自动终止会话的机制
- **密码哈希**（Password Hash）: 使用单向哈希算法（bcrypt）存储的密码，无法反向解密
- **重置令牌**（Reset Token）: 用于密码重置流程的一次性、时间限制的令牌

## 需求

### 需求 1: 用户注册

**用户故事**: 作为新用户，我希望能够创建账户，以便使用平台的功能和服务。

#### 验收标准

1. WHEN 用户提交包含有效数据的注册表单 THEN 系统 SHALL 创建新用户账户
2. THE 系统 SHALL 要求注册时提供以下字段：邮箱地址、用户名和密码
3. THE 系统 SHALL 验证邮箱地址格式有效
4. THE 系统 SHALL 验证用户名唯一，且仅包含字母、数字和连字符
5. THE 系统 SHALL 执行密码复杂度要求：至少 12 个字符，包含至少一个大写字母、一个小写字母、一个数字和一个特殊字符
6. IF 用户尝试使用已有的邮箱或用户名注册 THEN 系统 SHALL 拒绝注册并显示相应错误消息
7. WHEN 用户成功注册 THEN 系统 SHALL 向提供的邮箱地址发送验证邮件
8. THE 系统 SHALL 在存储前使用 bcrypt 对所有密码进行哈希处理，成本因子至少为 12

### 需求 2: 用户登录

**用户故事**: 作为注册用户，我希望能够使用用户名和密码登录系统，以便访问我的个人账户和订单历史。

#### 验收标准

1. WHEN 用户提交有效凭证 THEN 系统 SHALL 认证用户并返回访问令牌和刷新令牌
2. WHEN 用户提交无效凭证 THEN 系统 SHALL 返回错误消息“用户名或密码无效”并拒绝访问
3. IF 用户连续三次输入错误凭证 THEN 系统 SHALL 锁定账户 15 分钟
4. WHEN 用户账户被锁定 THEN 系统 SHALL 显示说明锁定时长的消息
5. WHEN 用户成功登录 THEN 系统 SHALL 创建包含用户 ID、登录时间戳和过期时间的会话记录
6. THE 系统 SHALL 在响应正文中返回访问令牌，并将刷新令牌设置为带有 HttpOnly 和 Secure 属性的 Cookie
7. THE 系统 SHALL 记录所有登录尝试（成功和失败），并包含时间戳、用户名和来源 IP 地址

### 需求 3: 会话管理

**用户故事**: 作为系统管理员，我希望系统能够自动管理用户会话的生命周期，以便确保安全性和资源的有效利用。

#### 验收标准

1. THE 系统 SHALL 将访问令牌的过期时间设置为签发后 15 分钟
2. THE 系统 SHALL 将刷新令牌的过期时间设置为签发后 7 天
3. WHILE 用户会话处于活动状态 THE 系统 SHALL 允许用户使用有效刷新令牌刷新访问令牌
4. WHEN 用户使用有效刷新令牌请求刷新令牌 THEN 系统 SHALL 签发新的访问令牌
5. WHILE 用户会话连续 30 分钟无活动 THE 系统 SHALL 自动终止会话并使刷新令牌失效
6. THE 系统 SHALL 限制每个用户最多拥有 5 个并发会话
7. WHEN 用户超过会话数量上限 THEN 系统 SHALL 终止最早的会话
8. WHEN 用户退出登录 THEN 系统 SHALL 使访问令牌和刷新令牌失效，并删除会话记录

### 需求 4: 令牌验证

**用户故事**: 作为系统，我需要验证用户的访问令牌，以便确保只有已认证的用户可以访问受保护的资源。

#### 验收标准

1. WHEN 用户使用有效访问令牌请求受保护的端点 THEN 系统 SHALL 允许请求继续执行
2. WHEN 用户使用已过期的访问令牌发起请求 THEN 系统 SHALL 返回 HTTP 401 状态及错误消息“令牌已过期”
3. WHEN 用户使用无效或格式错误的令牌发起请求 THEN 系统 SHALL 返回 HTTP 401 状态及错误消息“令牌无效”
4. WHEN 用户在未提供访问令牌的情况下发起请求 THEN 系统 SHALL 返回 HTTP 401 状态及错误消息“需要认证”
5. THE 系统 SHALL 使用配置的密钥验证令牌签名
6. THE 系统 SHALL 从验证通过的令牌中提取用户 ID，并提供给请求处理程序

### 需求 5: 密码重置

**用户故事**: 作为忘记密码的用户，我希望能够通过电子邮件重置密码，以便重新获得账户访问权限。

#### 验收标准

1. WHEN 用户请求重置密码 THEN 系统 SHALL 生成唯一重置令牌，并向用户注册邮箱发送重置链接
2. THE 系统 SHALL 生成具有密码学安全性、熵至少为 32 字节的重置令牌
3. THE 系统 SHALL 将重置令牌的过期时间设置为生成后 1 小时
4. WHEN 用户点击包含有效令牌的重置链接 THEN 系统 SHALL 显示密码重置表单
5. IF 重置令牌已过期 THEN 系统 SHALL 拒绝重置请求，并显示提示用户申请新链接的消息
6. WHEN 用户通过重置表单提交新密码 THEN 系统 SHALL 根据复杂度要求验证密码
7. WHEN 用户成功重置密码 THEN 系统 SHALL 使该用户所有现有会话和刷新令牌失效
8. WHEN 用户成功重置密码 THEN 系统 SHALL 向用户发送确认邮件
9. THE 系统 SHALL 同一时间仅允许每个用户拥有一个有效重置令牌

### 需求 6: 账户安全

**用户故事**: 作为用户，我希望我的账户受到保护，以便防止未经授权的访问。

#### 验收标准

1. THE 系统 SHALL 对每个 IP 地址实施每分钟 10 次登录尝试的速率限制
2. WHEN 某 IP 地址超过速率限制 THEN 系统 SHALL 返回 HTTP 429 状态，并阻止后续尝试 5 分钟
3. THE 系统 SHALL 记录所有安全相关事件，包括登录尝试、密码修改、密码重置和账户锁定
4. THE 系统 SHALL 将所有密码存储为成本因子至少为 12 的 bcrypt 哈希值
5. THE 系统 SHALL 不得在 API 响应中返回密码哈希值
6. THE 系统 SHALL 对所有认证相关端点使用 HTTPS
7. THE 系统 SHALL 为所有认证 Cookie 设置 Secure 和 HttpOnly 属性
8. THE 系统 SHALL 对所有更改状态的操作实施 CSRF 防护

### 需求 7: 用户登出

**用户故事**: 作为用户，我希望能够安全地登出系统，以便在共享设备上保护我的账户。

#### 验收标准

1. WHEN 用户退出登录 THEN 系统 SHALL 使当前访问令牌失效
2. WHEN 用户退出登录 THEN 系统 SHALL 删除刷新令牌 Cookie
3. WHEN 用户退出登录 THEN 系统 SHALL 从数据库删除会话记录
4. THE 系统 SHALL 提供“退出所有设备”选项，使该用户的所有会话失效
5. WHEN 用户退出所有设备 THEN 系统 SHALL 使该用户所有访问令牌和刷新令牌失效
```

#### 编写需求文档的最佳实践

1. **从简介开始**：先写简介章节，明确功能的范围和目标，这有助于后续需求的聚焦

2. **建立术语表**：在编写需求之前，先定义关键术语，确保一致性

3. **使用用户故事**：每个需求都应该有用户故事，说明"谁需要这个功能"和"为什么需要"

4. **应用 EARS 模式**：所有验收标准都应该使用 EARS 模式，确保清晰和一致性

5. **覆盖正常和异常流程**：不要只描述"快乐路径"，也要包含错误处理和边界条件

6. **保持原子性**：每个验收标准应该描述一个单一的行为，避免使用"and"合并多个行为

7. **使用可验证的标准**：避免模糊的词语（如"快速"、"用户友好"），使用可量化的标准

8. **引用术语表**：在需求中使用术语表中定义的术语，保持一致性

9. **考虑安全性**：对于涉及认证、授权、数据处理的功能，明确安全需求

10. **迭代改进**：需求文档不是一次性完成的，根据反馈和发现的缺口持续改进
